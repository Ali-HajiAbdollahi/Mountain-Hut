
# Technical Debt Management Strategy

This document records the decisions of our team on how we manage Technical Debt (TD) in the Mountain-Hut project: how code quality checks are part of every sprint (§1), how we pay back TD (§2) and how we decide on each issue (§3).

We accept some debt when it lets us deliver the sprint on time (a trade-off between "perfect" code and code that just works), but we manage it **explicitly**, so that we can plan it and avoid bad surprises.

We identify TD with **SonarQube Cloud** (automatic static analysis):
https://sonarcloud.io/project/overview?id=Ali-HajiAbdollahi_Mountain-Hut

The analysis covers the backend (`server`), the Flutter client (`client/lib`), the database scripts, the Dockerfile and the shell scripts. Two groups of folders are excluded:

- the native platform folders generated by Flutter (`client/android`, `ios`, `windows`, `linux`, `macos`), because they are template code;
- the test folders (`server/tests`, `client/test`, `client/e2e_test`, `client/test_driver`), because they check the application rather than being part of it. The tests are still run by the analysis to measure coverage.

---

## 1. Code quality checks within the sprint activities

### 1.1 Automatic analysis on every push and Pull Request

A GitHub Actions workflow (`.github/workflows/sonarcloud.yml`) runs on every push to `develop` and `main` and on every Pull Request. It runs the backend and frontend tests, produces the coverage reports and sends the analysis to SonarCloud. The result is shown on the SonarCloud dashboard and directly in the Pull Request.

SonarCloud reports four types of issues:

| Type             | Quality         | What it means for us                                                        |
| ---------------- | --------------- | --------------------------------------------------------------------------- |
| Code smell       | Maintainability | Code that is hard to change: complex methods, duplicated code, design flaws |
| Bug              | Reliability     | Code that can behave incorrectly                                            |
| Vulnerability    | Security        | Code that can be exploited                                                  |
| Security hotspot | Security        | Security-sensitive code that a person must review                           |

Besides line-level issues, we also look for the **code smells** seen in the course, especially **significant duplication**, **brain methods** and **god classes** (very large classes with many responsibilities), and **shotgun surgery** (a change that requires small edits in many files). SonarCloud highlights duplication and complexity; the other smells are checked during code review.

### 1.2 Quality gate

We use the **Sonar way** quality gate, checked on **new code** only. A Pull Request passes when its new code has:

- Security, Reliability and Maintainability rating **A**;
- coverage **≥ 80%**;
- duplicated lines **≤ 3%**;
- all security hotspots reviewed.

Checking new code stops the debt from growing, while the existing debt is paid back gradually (§2).

### 1.3 Pull Request workflow

- No direct pushes to `develop` or `main`: every change goes through a feature branch and a Pull Request.
- A Pull Request is merged only when the quality gate passes, all automated tests pass and at least one other team member has reviewed it, also looking at the SonarCloud report.
- If the gate fails, the author fixes the issues in the same Pull Request, or marks them on SonarCloud with a justification that the reviewer agrees with (§3).

### 1.4 Definition of Done

A user story is *Done* only if, in addition to its acceptance criteria:

- unit, integration and end-to-end tests are written and passing;
- the code has been reviewed and merged through a Pull Request;
- the Pull Request passed the SonarCloud quality gate.

## 2. How we pay back Technical Debt

### 2.1 Identification

TD items come from two sources:

- **SonarCloud issues** (§1.1);
- **debt found by the team**, which a static analysis tool cannot detect: missing tests, known defects, requirements only partially implemented, temporary workarounds. These are noted during code review and added to YouTrack.

### 2.2 Estimation

For each TD item we estimate:

- **Principal:** for SonarCloud issues we start from the *remediation effort* shown by the tool, and add the time needed to test the change. For the other items we use our historical effort data (the hours logged on similar tasks).
- **Interest amount:** how much the item slows us down or how much it would cost to deal with it later (e.g. a defect found by users instead of by tests). SonarCloud's **severity** (High, Medium, Low) is our first indicator.
- **Interest probability:** how likely the item is to cause problems, based on how often that code is used and changed and whether it reaches users. Code that is never shipped or never changed has a probability close to zero.

### 2.3 Prioritization

We decide whether to pay back an item by comparing its cost (principal) with its benefit (interest × probability). We pay first the **most profitable** items, with **low principal and high interest**, and we consciously ignore those that are not profitable.

We place each item in the cost/benefit matrix:

|                                  | **Low effort (principal)**                                     | **High effort (principal)**                         |
| -------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------- |
| **High impact (interest)** | **P1** – fix immediately                                      | **P2** – plan in the current or next sprint        |
| **Low impact (interest)**  | **P2** – fix when convenient, e.g. while working on that file | **Not paid** – accepted with a justification (§3) |

In addition, an item is always **P1** if it blocks the quality gate or is a High severity security or reliability issue in application code.

When two items have the same priority, we also consider the other criteria seen in the course: the **quality characteristic** affected (security first, then reliability, then maintainability), the **component or feature** (code we will change in the next sprints comes first) and the **user impact** (features used more often come first).

### 2.4 When the debt is paid back

**Debt repayment is a fixed part of every sprint**, next to the committed stories, testing and review:

- **Debt introduced by a Pull Request** is paid immediately: the Pull Request cannot be merged until the quality gate passes.
- **Existing debt** is selected at **sprint planning**: we look at the SonarCloud dashboard, choose the P1 items and as many P2 items as fit, and estimate them like any other task.
- About **5% of the sprint capacity** is reserved for TD repayment.
- If new High severity issues reach `develop`, fixing them takes priority over starting new stories.

### 2.5 Who pays it back (internal organization)

- The **author of a Pull Request** fixes the issues that the Pull Request introduces.
- Existing debt is **assigned at sprint planning**, preferably to the member who knows that part of the code best or to people who have less work to do. If the code was written recently by someone else, that person is informed before the change, to avoid conflicts.
- **One or two members** check the SonarCloud dashboard during the sprint, propose the TD items at planning and report the results at the retrospective.
- Team members with SonarCloud administration rights manage exclusions, accepted issues and quality gate settings.

### 2.6 How it is tracked

- **YouTrack:** every sprint has a task **"Fix technical debt issues"**, estimated at planning and assigned to the members who work on TD. The selected items are listed in its description, with the links to the SonarCloud issues. Time spent is logged on this task, separately from story tasks.
- **SonarCloud:** every issue keeps its status (open, fixed, accepted, false positive); accepted issues and false positives always have a comment with the reason.
- **Git:** TD fixes are committed and merged through a Pull Request like any other change.
- **Retrospective:** we report the TD hours estimated at planning versus the hours actually spent, how the SonarCloud ratings changed, and which kinds of issues keep appearing, so that we can prevent them.

## 3. Technical Debt decisions

Every issue reported by SonarCloud gets one of three decisions. The decision and its reason are recorded on SonarCloud, so the complete and up-to-date list is always available on the dashboard.

### Fixed

The issue is real and paying it back is worth the cost. This is the default decision for the code we write and maintain, in particular:

- security and reliability issues in the backend and in the Flutter client;
- duplicated code, which is moved into shared functions or widgets;
- issues in the files used to build and release the application (Dockerfile, CI workflow, scripts).

### Accepted

The issue is real, but its interest or its probability is close to zero, so paying it back is not profitable. Typical cases:

- the code is generated by a framework and not maintained by the team;
- the code is never shipped to users (e.g. native platforms we do not distribute);
- an external constraint prevents the fix and the risk is low (e.g. a tool version we cannot change).

An accepted issue is reconsidered if the situation changes, for example if we decide to ship a native app.

### False positive

The tool reports a problem that does not exist in our context, for example a rule that assumes a different technology from the one we use. The comment on SonarCloud explains why the rule does not apply.

Every *Accepted* or *False positive* decision is discussed with at least one other team member before it is marked on SonarCloud. The trade-offs we accept on quality are made explicit and visible to the whole team, instead of being left hidden in the code.
