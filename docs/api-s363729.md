# Mountain Hut — API Contract

API documentation for frontend and backend integration using Flutter Web.

## Configuration

Default local API base URL:

```text
http://localhost:3001/api
```

The endpoint paths documented below already include `/api`. Do not add this prefix twice.

The Flutter client is implemented in:

```text
client/lib/core/network/mountain_hut_api.dart
```

Endpoint constants are defined in:

```text
client/lib/core/network/api_endpoints.dart
```

The API base URL is configured through the `API_BASE_URL` compile-time variable:

```bash
flutter run -d chrome \
  --web-hostname localhost \
  --web-port 5173 \
  --dart-define=API_BASE_URL=http://localhost:3001/api
```

The backend's local `server/.env` must contain matching settings:

```dotenv
PORT=3001
CLIENT_ORIGIN=http://localhost:5173
```

Preserve the other environment variables, including the session secret and SMTP configuration.

The previous JavaScript adapter in `client/src/api/mountainHut.js` is not used by Flutter. Vite environment variables do not configure the Flutter application.

## Flutter HTTP Client

Import the API client:

```dart
import 'package:client/core/network/mountain_hut_api.dart';
```

Create an instance at the appropriate application scope and share it with the pages that need it:

```dart
final api = MountainHutApi();
```

Do not create the client inside a widget's `build()` method.

The client uses:

```dart
BrowserClient()..withCredentials = true
```

This enables browser-managed session cookies. The browser handles the session cookie; application code must not attempt to read the HTTP-only cookie.

Requests containing a JSON body use:

```http
Content-Type: application/json
```

The API client automatically encodes request bodies and decodes JSON responses.

This implementation targets Flutter Web. Native Android, iOS and desktop applications require a suitable HTTP client and cookie-management strategy.

Call `api.close()` only when the owning application component is disposed and the client is no longer needed.

## Endpoints

| Method and path | Required identity | Request | Successful response |
|---|---|---|---|
| GET `/api/health` | Public | None | 200 `{"status":"ok"}` |
| POST `/api/users` | Public | `name`, `email`, `phone`, `password` as strings | 201 public user profile and session cookie |
| POST `/api/sessions` | Public | `email`, `password` | 200 public user profile and session cookie |
| GET `/api/sessions/current` | Authenticated | None | 200 public user profile |
| DELETE `/api/sessions/current` | Any | None | 204 without a response body |
| GET `/api/timeslots?date=YYYY-MM-DD` | Public | Required `date` query parameter | 200 array of slots with tables, capacity and available seats |
| GET `/api/timeslots/:id` | Public | Positive ID in the path | 200 slot |
| POST `/api/timeslots` | Employee | `start_time`, `end_time`, and either `tables` or `copy_from_tsID` | 201 slot |
| PUT `/api/timeslots/:id/tables` | Employee | Either `tables` or `copy_from_tsID` | 200 updated slot, which must initially have no tables |
| GET `/api/availability?date=YYYY-MM-DD&time=HH:mm&partySize=N` | Public | `date`, `time`, `partySize` query parameters | 200 availability result with slot and allocation |
| POST `/api/bookings` | Hiker | `tsID`, `n_people`, optional `requirements` | 201 object containing `booking` and `notification` |
| GET `/api/bookings` | Hiker | None | 200 array of the authenticated hiker's bookings |
| GET `/api/bookings/:id` | Hiker who owns the booking | Positive ID in the path | 200 booking |
| POST `/api/bookings/:id/confirmation` | Hiker who owns the booking | Empty object `{}` | 200 object containing `bookingReference` and `notification` |

### Booking Modification Integration

The backend also exposes:

```http
PATCH /api/bookings/:id
```

This endpoint belongs to the booking-change implementation.

The current `MountainHutApi` client does not yet support `PATCH` and does not provide a booking-update method. The frontend and booking-change owners must agree on the accepted payload, document its rules and add the client method before connecting the edit-booking page.

Do not call an assumed `api.updateBooking()` method: it is not currently implemented in this client.

## Error Handling

Backend error responses use this structure:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Error description"
  }
}
```

| HTTP status | Meaning |
|---|---|
| 400 | Invalid request data |
| 401 | Missing session or invalid authentication |
| 403 | Unauthorized role or forbidden Origin |
| 404 | Resource does not exist or does not belong to the user |
| 409 | Conflict: insufficient capacity, duplicate booking, booking deadline passed or table layout already defined |
| 413 | Request body too large |
| 503 | Database temporarily busy |
| 500 | Internal server error |

The Dart client converts HTTP errors into `ApiException` objects with:

- `status`: HTTP status code.
- `code`: machine-readable error code.
- `message`: error description.

A request timeout produces an `ApiException` with:

```text
status: 0
code: TIMEOUT
```

Status `0` is a client-side value, not an HTTP response status.

Network failures may throw other exceptions. UI handlers must handle both `ApiException` and other request failures.

The UI may display `message`, but it should determine its behaviour using `status` and `code`.

Do not automatically retry a booking creation after a timeout or connection failure. The backend may already have committed the booking.

## Request Data Types

Numeric values in JSON request bodies must be numbers, not strings copied directly from text fields.

Correct:

```json
{
  "tsID": 5,
  "n_people": 5
}
```

For a Flutter text field, validate and convert the value before calling the API:

```dart
final people = int.tryParse(peopleController.text.trim());

if (people == null || people <= 0) {
  // Display a validation message and stop submission.
  return;
}
```

Query parameters are encoded as strings in the URL. The API client handles that conversion for `partySize`.

Dates and times use:

```text
Date: YYYY-MM-DD
Time: HH:mm
Slot timestamp: YYYY-MM-DD HH:mm
```

## Request Examples

The IDs and dates below are illustrative. Use IDs returned by the server and dates appropriate for the current booking window.

### Create a Timeslot

**Endpoint:** `POST /api/timeslots`

Times are expressed in the hut's local time zone, `Europe/Rome`.

```json
{
  "start_time": "2026-11-06 12:00",
  "end_time": "2026-11-06 13:00",
  "tables": [
    {
      "table_no": 1,
      "seats": 2
    },
    {
      "table_no": 2,
      "seats": 4
    },
    {
      "table_no": 3,
      "seats": 6
    }
  ]
}
```

Flutter call:

```dart
final slot = await api.createSlot(
  startTime: '2026-11-06 12:00',
  endTime: '2026-11-06 13:00',
  tables: [
    {'table_no': 1, 'seats': 2},
    {'table_no': 2, 'seats': 4},
    {'table_no': 3, 'seats': 6},
  ],
);

final slotId = slot['tsID'] as int;
```

The backend calculates total capacity from the tables.

### Create a Timeslot by Copying a Layout

**Endpoint:** `POST /api/timeslots`

This operation copies the source slot's tables and seating capacity without copying its bookings or occupancy.

```json
{
  "start_time": "2026-11-06 13:00",
  "end_time": "2026-11-06 14:00",
  "copy_from_tsID": 1
}
```

Flutter call:

```dart
final slot = await api.createSlot(
  startTime: '2026-11-06 13:00',
  endTime: '2026-11-06 14:00',
  copyFromTsId: sourceSlotId,
);
```

Provide either `tables` or `copyFromTsId`, never both.

### Define Tables for an Empty Slot

**Endpoint:** `PUT /api/timeslots/:id/tables`

Flutter call:

```dart
final updatedSlot = await api.defineTables(
  slotId,
  tables: [
    {'table_no': 1, 'seats': 4},
    {'table_no': 2, 'seats': 6},
  ],
);
```

To copy a layout instead:

```dart
final updatedSlot = await api.defineTables(
  slotId,
  copyFromTsId: sourceSlotId,
);
```

This operation defines the initial layout of a slot that has no tables. It does not modify an already-defined layout.

### Check Availability

**Endpoint:**

```http
GET /api/availability?date=2026-11-06&time=12:00&partySize=3
```

Authentication is not required.

Flutter call:

```dart
final result = await api.checkAvailability(
  date: '2026-11-06',
  time: '12:00',
  partySize: 3,
);
```

Example response:

```json
{
  "available": true,
  "partySize": 3,
  "slot": {
    "tsID": 5,
    "start_time": "2026-11-06 12:00",
    "end_time": "2026-11-06 13:00"
  },
  "allocation": [
    {
      "table_no": 2,
      "seats": 3
    }
  ]
}
```

If no matching slot exists, `slot` is `null`, `available` is `false` and `allocation` is empty.

If the slot exists but does not have enough free seats, `available` is `false` and `allocation` is empty.

Availability checking does not reserve seats. The booking endpoint checks availability again and determines the actual assignment when creating the booking.

### Create a Booking

**Endpoint:** `POST /api/bookings`

```json
{
  "tsID": 5,
  "n_people": 5,
  "requirements": [
    {
      "n_people": 1,
      "description": "Peanut allergy",
      "allergy": true
    },
    {
      "n_people": 2,
      "description": "Vegetarian",
      "allergy": false
    }
  ]
}
```

Flutter call:

```dart
final result = await api.book(
  slotId: selectedSlotId,
  people: numberOfPeople,
  requirements: [
    {
      'n_people': 1,
      'description': 'Peanut allergy',
      'allergy': true,
    },
    {
      'n_people': 2,
      'description': 'Vegetarian',
      'allergy': false,
    },
  ],
);

final booking = result['booking'] as Map<String, dynamic>;
final notification = result['notification'] as Map<String, dynamic>;

final bookingId = booking['bID'] as int;
final reference = booking['reference'] as String;
final notificationStatus = notification['status'] as String;
```

The API client translates the Dart arguments `slotId` and `people` into the backend fields `tsID` and `n_people`.

The authenticated hiker's identity comes from the session. Do not send a user ID or role in the request body.

## Booking Response Fields

The booking object contains:

| Field | Description |
|---|---|
| `bID` | Booking identifier |
| `reference` | Human-readable booking reference |
| `tsID` | Timeslot identifier |
| `uID` | Identifier of the hiker who owns the booking |
| `contact_name` | Contact person's name |
| `contact_phone` | Contact person's phone number, which may be null |
| `n_people` | Party size |
| `created_at` | Creation timestamp |
| `created_by` | Identifier of the employee who entered the booking, or null for a web booking |
| `start_time` | Timeslot start time |
| `end_time` | Timeslot end time |
| `tables` | Array of table assignments containing `table_no` and `seats` |
| `requirements` | Array of requirements containing `rID`, `n_people`, `description` and `allergy` |

For `POST /api/bookings`, the booking object is nested inside `result['booking']`.

For `GET /api/bookings/:id`, the response is the booking object directly.

For `GET /api/bookings`, the response is an array of booking objects.

### Date and Time Handling

- `created_at` follows SQLite's UTC timestamp convention.
- `start_time` and `end_time` represent local times in `Europe/Rome`.
- Slot timestamps do not include a UTC offset.
- Do not interpret slot timestamps as UTC or automatically convert them to the browser's local time zone.
- Display them as hut-local times, or use explicit time-zone handling if conversion is required.

## Integration with Team Components

### 1. Login and Registration — Ali

Login:

```dart
final user = await api.login(email, password);
```

Registration:

```dart
final user = await api.register(
  name: fullName,
  email: email,
  phone: phone,
  password: password,
);
```

Store the returned user profile in application state.

On page load or reload, retrieve the current session:

```dart
final user = await api.currentUser();
```

A 401 response means that there is no valid authenticated session.

Logout:

```dart
await api.logout();
```

Clear the user profile from application state after logout.

Do not store passwords in browser storage. A user ID stored in the browser is not proof of authentication: the server validates the session.

### 2. Timeslot Configuration — Melissa

Use `api.createSlot()` to create a slot and its table layout.

Use `api.getSlot(sourceSlotId)` to preview a source layout before copying it:

```dart
final sourceSlot = await api.getSlot(sourceSlotId);
```

Use `copyFromTsId` to copy the layout when creating a new slot or defining tables for an empty slot.

Do not request total capacity as a separate input field. The backend calculates it from the tables.

The current `defineTables()` operation does not edit an existing layout.

### 3. Booking Page

Load slots for the selected date:

```dart
final slots = await api.listSlots(selectedDate);
```

Keep the `tsID` of the selected slot.

Validate the party size before submission and pass it as an integer:

```dart
final result = await api.book(
  slotId: selectedSlotId,
  people: numberOfPeople,
  requirements: requirements,
);
```

The UI must:

- Submit once per user action.
- Disable the submit button while the request is pending.
- Restore the button state when the request finishes.
- Handle HTTP errors and network failures.
- Show success only after a successful backend response.
- Check `mounted` before updating widget state after an asynchronous operation.

### 4. Booking Confirmation

Read the booking and notification objects:

```dart
final booking = result['booking'] as Map<String, dynamic>;
final notification = result['notification'] as Map<String, dynamic>;

final reference = booking['reference'];
final status = notification['status'];
```

| Notification status | Information to display |
|---|---|
| `accepted` | Booking saved; confirmation email accepted by the SMTP server |
| `failed` | Booking saved; confirmation email could not be sent |
| `disabled` | Booking saved; email service is disabled |

`accepted` does not guarantee that the message has reached the recipient's inbox.

Email failure does not cancel a booking that has already been saved.

When SMTP is configured, allow confirmation resending:

```dart
final result = await api.resendConfirmation(bookingId);

final notification = result['notification'] as Map<String, dynamic>;
final status = notification['status'];
```

Resending a confirmation must not create another booking.

### 5. Booking Details

Retrieve the authenticated hiker's bookings:

```dart
final bookings = await api.myBookings();
```

Retrieve one booking:

```dart
final booking = await api.booking(bookingId);
```

The frontend must not choose another user's identity to retrieve bookings. Ownership is determined by the backend from the authenticated session.

### 6. Handling Conflicts and Uncertain Outcomes

For an HTTP 409 response:

- Display the backend's message.
- Refresh the relevant slot information.
- Do not automatically create another booking.

For a timeout or lost connection during booking creation:

- Explain that the outcome has not yet been confirmed.
- Retrieve the authenticated user's bookings.
- Check whether a booking exists for the selected `tsID`.
- If it exists, show that booking instead of submitting another POST.

Do not describe an uncertain request outcome as a definite booking failure.

### 7. Access Handling

| HTTP status | UI behaviour |
|---|---|
| 401 | Ask the user to log in again |
| 403 | Deny the action and display a permissions message |
| 404 | Display that the requested resource is unavailable |

Authentication, role and booking ownership checks remain mandatory in the backend.

### 8. Development Across Two Computers

`localhost` refers to the computer running the browser or process.

If the frontend and backend run on different computers:

- Configure `API_BASE_URL` with the backend's reachable address.
- Configure `CLIENT_ORIGIN` with the frontend's actual origin, including protocol, host and port.
- Prefer a frontend proxy or shared origin to simplify cookie handling.
- Do not configure CORS with wildcard origin `*` when using credentials.

Changing CORS alone does not remove browser cookie restrictions.
