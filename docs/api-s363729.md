# Mountain Hut — API Contract

API documentation for frontend and backend integration.

**Local base URL:** `http://localhost:3001/api`

The paths in the table already include the `/api` prefix. Do not add it twice.

## Endpoints

| Method and path | Required identity | Request | Successful response |
|---|---|---|---|
| GET `/api/health` | Public | None | 200 `{"status":"ok"}` |
| POST `/api/users` | Public | `name`, `email`, `phone`, `password` as strings | 201 public user profile and session cookie |
| POST `/api/sessions` | Public | `email`, `password` | 200 public user profile and session cookie |
| GET `/api/sessions/current` | Authenticated | None | 200 public user profile |
| DELETE `/api/sessions/current` | Any | None | 204 without a response body |
| GET `/api/timeslots?date=YYYY-MM-DD` | Public | Required `date` query parameter | 200 array of slots with tables, capacity and available seats |
| GET `/api/timeslots/:id` | Public | Positive ID in the path | 200 slot |
| POST `/api/timeslots` | Employee | `start_time`, `end_time`, and either `tables` **or** `copy_from_tsID` | 201 slot |
| PUT `/api/timeslots/:id/tables` | Employee | Either `tables` **or** `copy_from_tsID` | 200 updated slot, which must initially have no tables |
| POST `/api/bookings` | Hiker | `tsID`, `n_people`, optional `requirements` | 201 `{"booking": …, "notification": …}` after MH-38 |
| GET `/api/bookings` | Hiker | None | 200 array of the authenticated hiker’s bookings |
| GET `/api/bookings/:id` | Hiker who owns the booking | Positive ID in the path | 200 booking |
| POST `/api/bookings/:id/confirmation` | Hiker who owns the booking | Empty object `{}` | 200 `{"bookingReference": …, "notification": …}` |

The `notification` field and confirmation resend endpoint are available after implementing MH-38.

Requests with a JSON body must use:

```http
Content-Type: application/json
```

The frontend must include session cookies in API requests:

```javascript
credentials: 'include'
```

## Error Handling

Error responses use the following format:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Error description"
  }
}
```

| HTTP status | Meaning |
|---|---|
| 400 | Invalid request data |
| 401 | Missing session or invalid authentication |
| 403 | Unauthorized role or forbidden Origin |
| 404 | Resource does not exist or does not belong to the user |
| 409 | Conflict: insufficient capacity, duplicate booking, booking deadline passed or table layout already defined |
| 413 | Request body too large |
| 503 | Database temporarily busy |
| 500 | Internal server error |

The UI may display `error.message`, but it must determine its behaviour using the HTTP status and `error.code`.

All numeric values in the request body must be **JSON numbers**, rather than strings taken directly from HTML inputs.

Correct example:

```json
{
  "tsID": 5,
  "n_people": 5
}
```

## Request Examples

### Create a Timeslot

**Endpoint:** `POST /api/timeslots`

Times are expressed in the hut’s local time zone, `Europe/Rome`.

```json
{
  "start_time": "2026-11-06 12:00",
  "end_time": "2026-11-06 13:00",
  "tables": [
    {
      "table_no": 1,
      "seats": 2
    },
    {
      "table_no": 2,
      "seats": 4
    },
    {
      "table_no": 3,
      "seats": 6
    }
  ]
}
```

### Create a Timeslot by Copying a Layout

**Endpoint:** `POST /api/timeslots`

This operation copies the source slot’s tables and seating capacity without copying its bookings or occupancy.

```json
{
  "start_time": "2026-11-06 13:00",
  "end_time": "2026-11-06 14:00",
  "copy_from_tsID": 1
}
```

Provide either `tables` or `copy_from_tsID`, never both.

### Create a Booking

**Endpoint:** `POST /api/bookings`

```json
{
  "tsID": 5,
  "n_people": 5,
  "requirements": [
    {
      "n_people": 1,
      "description": "Peanut allergy",
      "allergy": true
    },
    {
      "n_people": 2,
      "description": "Vegetarian",
      "allergy": false
    }
  ]
}
```

The IDs in these examples are illustrative. Always use the IDs returned by the server.

## Booking Response Fields

The booking object contains:

| Field | Description |
|---|---|
| `bID` | Booking identifier |
| `reference` | Human-readable booking reference |
| `tsID` | Timeslot identifier |
| `uID` | Identifier of the hiker who owns the booking |
| `contact_name` | Contact person’s name |
| `contact_phone` | Contact person’s phone number |
| `n_people` | Party size |
| `created_at` | Creation timestamp |
| `created_by` | Identifier of the employee who entered the booking, or `null` for a web booking |
| `start_time` | Timeslot start time |
| `end_time` | Timeslot end time |
| `tables` | Array of table assignments `{table_no, seats}` |
| `requirements` | Array of requirements `{rID, n_people, description, allergy}` |

For `POST /api/bookings`, the booking object is available in `result.booking`.

### Date and Time Handling

- `created_at` follows SQLite’s UTC timestamp convention.
- `start_time` and `end_time` represent local times in the `Europe/Rome` time zone.
- Do not automatically interpret these local values using `new Date(databaseString)` in the browser. Handle the hut’s time zone explicitly.

## Integration with Team Components

### 1. Login — Ali

Call:

```javascript
api.login(email, password)
```

Store the returned user profile in the application state.

When the page loads or reloads, retrieve the current session using:

```javascript
api.currentUser()
```

Do not store passwords in `localStorage`. A user ID stored in the browser is not proof of authentication: the server validates the session.

### 2. Timeslot Configuration — Melissa

Use:

```javascript
api.createSlot({
  start_time,
  end_time,
  tables
})
```

To copy an existing layout, send:

```javascript
api.createSlot({
  start_time,
  end_time,
  copy_from_tsID
})
```

To preview the source slot:

```javascript
api.getSlot(tsID)
```

The backend calculates total capacity from the table layout. Do not request it as a separate input field.

### 3. Booking Page

Load the slots for the selected date:

```javascript
api.listSlots(date)
```

Keep the selected `tsID` and convert numeric input values using `Number`.

Submit the booking once:

```javascript
api.book({
  tsID,
  n_people,
  requirements
})
```

Disable the submit button while the request is pending to avoid duplicate submissions.

### 4. Booking Confirmation

Display the booking reference and details using:

```javascript
result.booking
```

Handle `result.notification.status` as follows:

| Status | Information to display |
|---|---|
| `accepted` | Booking saved; confirmation email accepted by the SMTP server |
| `failed` | Booking saved; confirmation email could not be sent |
| `disabled` | Booking saved; email service is disabled |

`accepted` does not guarantee that the message has already reached the recipient’s inbox.

When SMTP is configured, allow the user to resend the confirmation using:

```javascript
api.resendConfirmation(bID)
```

Resending a confirmation must not create another booking.

### 5. Booking Details

To retrieve the authenticated hiker’s bookings:

```javascript
api.myBookings()
```

To retrieve a specific booking:

```javascript
api.booking(bID)
```

The frontend must not choose which user’s bookings to retrieve. The backend determines ownership from the authenticated session.

### 6. Handling HTTP 409 Conflicts

Reload the slot and display the message returned by the server.

Do not automatically submit another booking request.

If the response to the initial request was lost, retrieve the user’s bookings and check whether a booking already exists for the selected `tsID`.

### 7. Access Handling

| HTTP status | UI behaviour |
|---|---|
| 401 | Ask the user to log in again |
| 403 | Deny the action and display a message consistent with the user’s permissions |
| 404 | Display a message stating that the resource is unavailable |

Authentication, role and booking ownership checks remain mandatory in the backend.

### 8. Development Across Two Computers

`localhost` always refers to the computer running the browser or process.

If the frontend is opened on one teammate’s computer while the backend runs on another computer:

- Configure the frontend’s API base URL with the backend’s reachable address.
- Configure `CLIENT_ORIGIN` with the frontend’s actual origin, including protocol, host and port.
- Prefer a frontend proxy or a shared origin to simplify cookie handling.
- Do not configure CORS with the wildcard origin `*` when using credentials.
